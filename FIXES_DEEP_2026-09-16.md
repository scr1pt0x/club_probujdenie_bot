# Исправления усиленного аудита

Статус: реализовано и проверено локально, **не опубликовано и не установлено на сервер**.
Базовая версия: `55533d3`. Платежи, рассылки и исключения реальных участниц не выполнялись.

## Исправления семи проблем

1. Подтверждение оплаты сохраняет наибольший уже выданный срок, grace и срок
   отсрочки. Ручная выдача/продление также не сокращают обещанный срок.
2. Ошибка ответа Telegram на кнопку или обновления меню не прерывает доставку.
   Состав кампании и ссылка на исходное сообщение сохраняются в БД до отправки.
   В разделе рассылок есть история и продолжение после прерывания/перезапуска.
   Продолжение не повторяет получателей, для которых уже зафиксирована попытка.
3. Явное административное исключение сохраняет `users.access_suspended`.
   Проверки входа, ссылок, checkout и подтверждения оплаты учитывают его.
   Оплата сохраняется как финансовый факт, но не снимает ручное ограничение.
   «Выдать доступ», «Продлить на 7 дней» и включение льготы явно восстанавливают
   доступ. Неопределённые старые исключения автоматически не классифицируются.
4. Аудитории активных/бывших используют ту же SQL-политику прав, что проверка
   доступа: льгота, участие, grace, отсрочка, оплаченный поток, ручное ограничение.
5. Цена продления учитывает сохранённый grace, а не пересчитывает его по новым
   настройкам задним числом.
6. Расписание выбирает доступный для оплаты поток тем же запросом, что checkout;
   текущий поток показывается отдельно, если это другой поток. Окно набора видно.
   Старые статические даты заменяются динамическим отображением без удаления
   сохранённого текста. При редактировании обязательны `{start}`, `{end}`,
   `{sales_status}`; `{kind}` необязателен.
7. В админке добавлена очередь `needs_review`: карточка, проверка в YooKassa,
   явный выбор потока с подтверждением. Проверяются сумма, валюта, идентификатор
   заказа и принадлежность участнице. Возможные подтверждённые исходы:
   оплачено → участие; отменено → failed; ещё не завершено → pending.
   Повторная обработка не выдаёт доступ и не меняет поток второй раз.

## Дополнительная надёжность БД

- `0008_user_access_suspended`: новый флаг по умолчанию false. Никто из существующих
  пользователей не блокируется из-за установки; `access_exempt` не меняется.
- Старые revision ID длиннее стандартного поля Alembic. Поле версии расширяется
  без переименования опубликованных миграций; установка с нуля теперь проходит.
- `0009_schema_alignment`: недостающие индексы и NOT NULL, уже объявленные моделями.
  Если в старых данных есть NULL-флаги типа потока/администратора, миграция безопасно
  остановится, не угадывая их значения. Нужна явная проверка таких записей.
- Архивная таблица `promos` сохраняется; autogenerate не предлагает удалить её.
- Откат `0008` удаляет новый флаг, поэтому на production он не должен выполняться
  вслепую после использования ручных ограничений. При аварии предпочтителен откат
  кода с сохранением добавленных колонок и резервной копии.

## Проверки

126 тестов проходят с `TEST_DATABASE_URL` отдельной PostgreSQL; это на 32 больше
прежнего набора. Включены:

- оплата после ручного продления → обе задачи исключения не удаляют участницу;
- сохранение более длинной отсрочки/grace, цена после изменения настройки;
- реальный административный обработчик: исключение → запрет входа → восстановление;
- отказ в ручном исключении льготницы; сохранение финансовой истории;
- отсутствие разблокировки при новом и уже подтверждённом платеже;
- проверки checkout, ссылок, ручной проверки оплаты и заявки на вступление;
- ошибка ответа/редактирования Telegram перед отправкой рассылки;
- прерывание доставки → новая сессия БД → продолжение без повторной отправки;
- разные исходы ручной проверки платежа, несовпадение суммы, отказ провайдера,
  отсутствие потока, ручное ограничение и повторное нажатие;
- закрытие новых административных действий от неадминистратора;
- прежние тесты /Start, маршрутизации текста/медиа, платежных гонок и льгот.

Отдельно проверены: полная цепочка миграций с пустой БД, переход с `0007` на `0009`,
обратный переход и повторный upgrade. Восемь тестовых льготниц сохраняются;
`alembic check`: No new upgrade operations detected. Ruff, форматирование,
компиляция Python, `pip check`, `git diff --check` — без ошибок.

## Ограничения и установка

- Неоднозначная попытка Telegram-доставки не повторяется автоматически: сообщение
  могло уже прийти. В статистике явно разделены доставка, ошибки, неопределённость
  и пропуски; при продолжении показываются результаты именно этого запуска.
- История продолжения работает для новых кампаний с сохранённым составом. Старые
  кампании без этих данных нельзя безопасно восстановить автоматически.
- Несовпадающие с заказом данные YooKassa нельзя «подтвердить любой ценой»:
  администратор видит причину; спор требует сверки с разработчиком/провайдером.
- Неизвестная прежняя блокировка одной льготницы этим выпуском не снимается.
- Настоящая оплата и доставка реальным пользователям не тестировались. Успешные
  тесты не гарантируют доступность внешних сервисов и отсутствие всех будущих ошибок.

Для публикации нужен отдельный согласованный выпуск: резервная копия БД/приложения,
проверка NULL-флагов и сохранения 8 льготниц, миграции перед запуском нового кода,
проверка healthcheck, polling, логов и dry-run кандидатов на исключение. Серверные
пользовательские скрипты сохранить; массовые рассылки и восстановление доступа
не запускать для проверки выпуска.
